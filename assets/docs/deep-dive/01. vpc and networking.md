# Session 1 — VPC & Networking

## What it is

A VPC (Virtual Private Cloud) is your private, isolated network inside AWS. Think of it as buying a plot of land inside AWS's data center — you define the boundaries, the internal roads, and who gets in or out.

Everything in your system — EKS nodes, RDS, Redis, Ray workers — lives inside this VPC. Nothing is directly reachable from the internet unless you explicitly allow it.

---

## My specific setup

### Full-scale (dev/aws-full-scale)

- CIDR: 10.0.0.0/16 — 65,536 private IPs
- 3 Availability Zones: us-east-1a, us-east-1b, us-east-1c
- 3 subnet tiers across each AZ:
  - Public subnets (10.0.1–3.0/24) — Load balancers, NAT Gateways
  - Private subnets (10.0.101–103.0/24) — EKS nodes, Ray workers
  - Database subnets (10.0.201–203.0/24) — RDS, ElastiCache
- One NAT Gateway per AZ (3 total)
- DNS hostnames + DNS support enabled


### Minimal (main)
- Same CIDR, same subnet structure
- 2 AZs only (us-east-1a, us-east-1b)
- Single NAT Gateway — one point of failure, saves ~$65/month

## The three subnet tiers — why each exists

### Public subnets
These have a route to the Internet Gateway directly. Only two things live here: the Application Load Balancer (entry point for user traffic) and NAT Gateways. Nothing else is public-facing.

### Private subnets
No direct internet route. EKS nodes and Ray workers live here. They reach the internet (to pull Docker images, download models) only via the NAT Gateway in the public subnet. Inbound from internet — impossible.

### Database subnets
Further isolated. RDS and ElastiCache live here. No route to internet at all — not even via NAT. The only traffic allowed in is from within the VPC CIDR (10.0.0.0/16), enforced by Security Groups on each resource.

**The layered isolation matters:** even if an EKS node is compromised, the attacker can't reach RDS directly — they'd have to break through the Security Group rules that only allow port 5432 from VPC-internal IPs.

---

## NAT Gateway — what it actually does

Your EKS nodes sit in private subnets. They need to pull images from ECR, download model weights from HuggingFace, call external APIs. But they have no public IP.

NAT Gateway sits in the public subnet with a public IP. Private subnet traffic routes to it, NAT Gateway translates the source IP to its own public IP, sends the request out, gets the response, translates back. Outbound only — no inbound connections can be initiated from internet.

**Why one NAT per AZ in full-scale:**
NAT Gateway is AZ-scoped. If you have one NAT in us-east-1a and that AZ has an outage, your nodes in us-east-1b and us-east-1c lose internet egress too — they can't pull images, can't download models. One NAT per AZ means each AZ is self-sufficient. The tradeoff is cost: ~$32/month per NAT Gateway plus data transfer charges.

**Why single NAT in minimal:**
Acceptable for dev — if the NAT goes down during testing, you restart it. In prod that's a P0 incident.

## Security Groups — how your services are locked down

Security Groups are stateful firewalls at the resource level. Your configs define them explicitly for each stateful service:

| Resource | Allowed inbound | Source |
|---|---|---|
| RDS PostgreSQL | Port 5432 | VPC CIDR (10.0.0.0/16) |
| ElastiCache Redis | Port 6379 | VPC CIDR |
| Neo4j | Port 7687 (Bolt), 7474 (HTTP) | VPC CIDR |
| EKS nodes | Managed by EKS module | Node-to-node + control plane |

None of these are reachable from outside the VPC. The API is only reachable via the Ingress controller → ALB in the public subnet.

## Subnet tagging — why it matters for Kubernetes

Your VPC module applies specific tags to subnets:

```terraform
public_subnet_tags = {
    "kubernetes.io/role/elb" = "1"
}
private_subnet_tags = {
    "kubernetes.io/role/internal-elb" = "1"
    "karpenter.sh/discovery" = var.cluster_name
}
```

- `kubernetes.io/role/elb` tells the AWS Load Balancer Controller which subnets to place public-facing ALBs in.
- `kubernetes.io/role/internal-elb` tells it where to place internal load balancers (inter-service traffic).
- `karpenter.sh/discovery` tells Karpenter which subnets it's allowed to provision new EC2 nodes into. Without this tag, Karpenter won't know where to launch nodes and pending pods will stay unscheduled.

These tags are not cosmetic — missing them breaks ALB provisioning and Karpenter node discovery silently.

## How networking flows end-to-end in your system

```
User request 
↓
Internet Gateway (public)
↓
Application Load Balancer (public subnet)
↓
NGINX Ingress Controller (private subnet, EKS)
↓
API Service pod (private subnet)
↓
Ray Serve LLM / Embed (private subnet)
Ray workers (private subnet)
Qdrant / Neo4j (private subnet)
↓
RDS / Redis (database subnet — no internet route at all)
```

Outbound only (model downloads, ECR pulls):

```
EKS node / Ray worker (private subnet)
↓
NAT Gateway (public subnet)
↓
Internet → ECR / HuggingFace / external APIs
```

## Trade-offs made

**Why not put everything in public subnets and skip NAT?**
> "Cheaper and simpler, but any misconfigured Security Group or exposed port becomes a direct attack surface. Private subnets mean even a misconfiguration doesn't automatically mean internet exposure. Defense in depth — network isolation is the first layer."

**Why not a single flat subnet?**
> "Flat subnets mix compute, data, and ingress in the same network segment. Database subnet isolation means even with full access to a compute node, an attacker still can't reach RDS without hitting the Security Group rules.It also gives you clean network ACLs if you need an extra layer beyond Security Groups."

**Why Terraform module for VPC instead of manual console setup?**
> "Reproducibility and drift prevention. The VPC module encapsulates subnet calculation, route table creation, NAT Gateway association, and subnet tagging in one declaration. Manual setup drifts — someone adds a rule in the console and it's not in source control. Terraform detects and corrects that drift on the next apply."

## Likely interview questions

**Q: Why three subnet tiers instead of two?**
> "Public/private is the minimum. The database tier adds an extra isolation boundary — database subnets have no NAT route at all, so even if a node in the private subnet is compromised the attacker can't pivot to RDS via internet egress. It also makes Security Group rules cleaner — you allow port 5432 only from the private subnet CIDR, not the whole VPC."

**Q: What happens if your single NAT Gateway goes down in the minimal setup?**
> "All private subnet nodes lose internet egress. No new Docker image pulls, no model downloads, no external API calls. Existing connections keep working until they time out. For dev that's acceptable — I'd restart the NAT. In prod I'd have one NAT per AZ and accept the ~$65/month cost because the alternative is a full cluster outage on an AZ event."

**Q: How does Karpenter know which subnets to provision nodes in?**
> "The `karpenter.sh/discovery` tag on private subnets. Karpenter reads that tag to build its list of eligible subnets for node provisioning. It also uses the same tag on Security Groups to know which SGs to attach to new nodes. Without those tags, Karpenter can see pending pods but can't place nodes — the pods stay in Pending indefinitely."

**Q: Why enable DNS hostnames on the VPC?**
> "EKS requires it. Kubernetes service discovery relies on DNS — pods resolve each other by service name, not IP. Without DNS hostnames enabled, the EKS control plane can't assign DNS names to nodes and CoreDNS can't function. It also lets RDS and ElastiCache generate hostnames you can reference in config rather than hardcoding IPs that change on failover."

## One-liner summary to open with in an interview

> "I set up a three-tier VPC across multiple AZs — public subnets for the load balancer and NAT, private subnets for compute, isolated database subnets for RDS and Redis with no internet route. Karpenter subnet discovery and ALB placement are both driven by subnet tags defined in Terraform."
