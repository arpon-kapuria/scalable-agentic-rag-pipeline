# Session 2 — EKS + Karpenter

## What EKS is

EKS (Elastic Kubernetes Service) is AWS's managed Kubernetes control plane. Kubernetes is a container orchestration system — it decides where containers run, restarts them if they crash, handles networking between them, and manages rolling deployments.

"Managed" means AWS runs the control plane (API server, etcd, scheduler) for you. You only manage the worker nodes — the EC2 instances where your actual pods run.

## The system node group — what it actually runs

This is your always-on baseline. It does not run your application workloads. It runs cluster infrastructure:

- **CoreDNS** — Kubernetes internal DNS, every service-to-service call uses it
- **Karpenter** itself — the autoscaler that provisions app nodes
- **AWS Load Balancer Controller** — provisions ALBs from Ingress manifests
- **EBS CSI Driver** — allows pods to claim EBS volumes (Qdrant, Neo4j PVCs)
- **External Secrets Operator** — syncs AWS Secrets Manager → K8s secrets
- **Metrics Server** — feeds resource metrics to HPA and Ray autoscaler

**Why m6i.large in full-scale, not t3:**
t3 is burstable — it uses CPU credits. Under sustained load (Karpenter constantly reconciling, CoreDNS handling thousands of service lookups) it burns through credits and throttles. m6i is fixed performance — 2 full vCPUs always available. You cannot afford Karpenter to get CPU-throttled because that delays node provisioning, which delays pod scheduling, which causes request timeouts.

## The taint — why it exists and why you removed it

### Full-scale: taint present
```yaml
taints:
  - key: "CriticalAddonsOnly"
    value: "true"
    effect: "NO_SCHEDULE"
```

`NO_SCHEDULE` means: no pod will be scheduled on this node unless it has a matching **toleration** in its spec. CoreDNS, Karpenter, and system add-ons have that toleration baked in. Your Ray workers, API pods, Qdrant — they don't. So they can never land on the system node group.

**Why this matters:** Without the taint, a burst of Ray ingestion jobs could fill the system node's CPU and memory, starving CoreDNS. CoreDNS goes down, all DNS resolution inside the cluster fails, every service-to-service call breaks. Your entire system collapses because a chunking job took too much RAM.

### Minimal: taint removed
With 1 node, you have no choice. Everything — CoreDNS, Karpenter, API pods, Ray head — shares that single t3.medium. It works for dev but it's exactly the failure mode above waiting to happen under any real load.

## IRSA — why it's enabled on EKS

```hcl
enable_irsa = true
```

IRSA (IAM Roles for Service Accounts) lets a specific Kubernetes pod assume a specific AWS IAM role — without storing any AWS credentials inside the cluster.

How it works:
1. EKS exposes an OIDC endpoint
2. Terraform registers that endpoint with AWS IAM as a trusted identity provider
3. A Kubernetes Service Account is annotated with an IAM role ARN
4. When a pod using that service account makes an AWS API call, EKS injects a signed OIDC token, AWS validates it, and grants the role

In your system: Ray worker pods use IRSA to read/write S3. They never have an AWS access key — no credentials to rotate, no credentials to leak.

## What Karpenter is

Karpenter is a node autoscaler. When a pod can't be scheduled because no existing node has enough resources, Karpenter provisions a new EC2 instance in seconds, the pod schedules on it, and when the pod is done Karpenter terminates the node.

This is fundamentally different from the old Cluster Autoscaler:
- Cluster Autoscaler scales pre-defined node groups (ASGs) — you declare instance types upfront
- Karpenter provisions any instance type that fits the pod's resource request
  — it selects the cheapest option at the moment of need

## Your two Karpenter provisioners

### CPU Provisioner

**Full-scale:**
```yaml
instance-family: ["m6i", "c6i", "r6i"]   # general, compute, memory optimized
capacity-type: ["spot"]
cpu limit: 1000
consolidation: enabled
```

**Minimal:**
```yaml
instance-family: ["t3"]                   # cheapest only
capacity-type: ["spot"]
cpu limit: 8                              # hard financial cap
consolidation: enabled
```

**Instance family choices explained:**
- `m6i` — general purpose, balanced CPU/RAM — for API pods, Ray head
- `c6i` — compute optimized, higher CPU:RAM ratio — for ingestion workers doing CPU-heavy chunking, tokenization, graph extraction
- `r6i` — memory optimized — for large embedding batches or Neo4j if moved to a node
- `t3` (minimal) — burstable, cheapest, fine for low-sustained workloads

**Spot instances:** EC2 spare capacity sold at 60-90% discount. AWS can reclaim with 2-minute warning. Acceptable for stateless Ray workers — if a spot node is reclaimed, Ray reschedules the task on another worker. Not acceptable for stateful workloads like Neo4j or RDS (which is why those aren't on Karpenter nodes).

**Consolidation:** Karpenter actively watches for underutilized nodes and evicts pods to pack them onto fewer nodes, then terminates the empty ones. Without consolidation, a node that finishes its work sits idle burning money until the TTL expires.

---

### GPU Provisioner

**Full-scale:**
```yaml
instance-category: ["g", "p"]
instance-generation: Gt "4"              # g5+, p4d+ only
capacity-type: ["on-demand", "spot"]
nvidia.com/gpu limit: 100
ttlSecondsAfterEmpty: 30
```

**Minimal:** Entirely commented out — no GPU provisioner exists.

**Instance category breakdown:**
- `g` family — inference-optimized GPUs (g5: A10G, g4dn: T4)
- `p` family — training-grade GPUs (p4d: A100, p3: V100)
- Generation `> 4` filter excludes g4dn (T4) and older — you want A10G minimum for vLLM with AWQ on 70B

**Why on-demand + spot mix for GPU:**
GPU spot availability is lower than CPU spot. An inference replica getting terminated mid-request causes a visible error. The mix lets Karpenter try spot first (cheaper) but fall back to on-demand if no spot capacity exists. For the LLM service where availability matters more than cost, on-demand is the safer base.

**`ttlSecondsAfterEmpty: 30`:**
A GPU node costs ~$1-3/hour depending on instance. 30 seconds after the last GPU pod exits, Karpenter terminates the node. If you set this to 5 minutes and you have bursty traffic, you pay for 4+ minutes of idle GPU per burst. At scale across 20 GPU nodes that's significant. The 30-second window is tight enough to save money while giving in-flight requests time to finish draining.

## How Karpenter and Ray autoscaler interact

This is a two-layer autoscaling system and the interaction is important:

```
User traffic spike
       ↓
Ray Serve: target_num_ongoing_requests_per_replica exceeded
       ↓
Ray requests a new replica (new Ray actor)
       ↓
Ray actor needs resources — no node has capacity
       ↓
Pod goes Pending
       ↓
Karpenter sees Pending pod, reads resource requests
       ↓
Karpenter selects cheapest fitting EC2 instance
       ↓
EC2 node joins cluster (~60s for CPU, ~90s for GPU)
       ↓
Pod schedules, Ray actor starts, replica becomes available
```

Ray autoscaler handles Ray-level resource allocation. Karpenter handles EC2-level node provisioning. They don't conflict — they operate at different layers.

## KMS encryption — why disabled in minimal

```hcl
# minimal only
create_kms_key            = false
cluster_encryption_config = {}
```

KMS encrypts Kubernetes secrets stored in etcd at rest. In full-scale this is standard practice — secrets like API keys and DB passwords in etcd are encrypted with a customer-managed KMS key.

Disabled in minimal because: KMS costs $1/month per key plus $0.03 per 10,000 API calls. Trivial in prod. Also KMS key creation and rotation adds IAM complexity that slows down dev iteration. Acceptable trade-off for a dev environment with no real secrets.

## Trade-offs to articulate

**Why EKS over ECS or plain EC2?**
> "ECS is simpler but ties you to AWS primitives. Kubernetes gives me portable manifests — the same Helm chart runs locally with kind or on any cloud. Ray, KubeRay, and Karpenter all have first-class K8s support. ECS has no equivalent to KubeRay's RayCluster CRD."

**Why Karpenter over Cluster Autoscaler?**
> "Cluster Autoscaler scales pre-defined ASG node groups — I'd have to declare a GPU node group upfront and pay for it even when idle. Karpenter provisions on demand, selects the cheapest fitting instance type at the moment of need, and terminates nodes in 30 seconds when empty. For GPU workloads that's the difference between paying for idle GPU time and paying only for actual inference time."

**Why spot for CPU workers but on-demand option for GPU?**
> "CPU Ray workers are stateless and fault-tolerant — Ray retries tasks on spot reclamation. GPU inference replicas are stateful mid-request. A spot reclaim during token generation causes a visible error to the user. The cost difference on GPU spot vs on-demand is meaningful but not worth the reliability hit on the inference path."

## Likely interview questions

**Q: What's the difference between EKS managed node groups and Karpenter?**
> "Managed node groups are static pools — you define instance type, min, max, and AWS manages the ASG. They're always running at min_size. Karpenter is dynamic — it provisions nodes only when there are pending pods and terminates them when empty. For my system, the managed node group runs the system add-ons permanently. Karpenter handles all application workload nodes — Ray workers, API replicas — provisioning and terminating them on demand."

**Q: How does a pod get scheduled on a GPU node?**
> "Three things have to align. The pod requests `nvidia.com/gpu: 1` in its resource spec. Karpenter's GPU provisioner sees the pending pod, matches the GPU resource request, and provisions a g5 node. The NVIDIA device plugin daemonset on that node advertises the GPU as an allocatable resource to the Kubernetes scheduler. The scheduler then binds the pod to that node. If any of those three are misconfigured — wrong resource request, missing toleration for the GPU taint, device plugin not running — the pod stays Pending."

**Q: What happens when a spot node gets reclaimed mid-ingestion?**
> "Ray gets a 2-minute SIGTERM warning from EC2 before reclamation. Ray's fault tolerance kicks in — the task running on that worker is marked failed and rescheduled on another available worker. If no worker is available, Karpenter provisions a new spot node and the task runs there. The ingestion job is delayed but not lost. This works because Ray tasks are designed to be idempotent — re-running a chunking or embedding task on the same document produces the same output."

**Q: Why did you set `num-cpus: 0` on the Ray head node?**
> "The head node manages scheduling, the dashboard, and cluster state. If it also runs compute tasks, a heavy ingestion job can starve the scheduler of CPU, causing task assignment delays across the whole cluster. Setting `num-cpus: 0` tells Ray's scheduler to never assign tasks to the head node — it only orchestrates. All actual work goes to worker nodes."
